### 直した原因(詳しくは design_decisions.md 11d)
| 版 | 見つけた原因 | 直し方 |
|---|---|---|
| v1 | 入口の手前の点が軸からずれていて、斜めに脚の列に入った / 入口で測っていた / 回りながら入った / 経路計画が入口で輪を作った | 手前の点を軸の上に、入口の 0.15m 手前で止まって測る、経路計画の設定 |
| v3 | **入口の手前で隣の椅子を測って、その椅子の誤差に合わせて補正**(3回)/ 壁ぎわの出口から斜めに出た | 状態機械の目標(/goal_pose)から入る椅子を決める / 椅子の横の面に沿って離れる |
| v4 | 出口から次への直線が隣の椅子の角を 1cm でかすめた | 直線にも余白 3cm、入口の手前には突入の向きで着く |
| v5 | 関係ない遠くの椅子の角を回る点に選んだ / 回る点の手前で角に近づいた | 目標に近づく点だけ、回る点は椅子から 5〜7cm |
| v6 | 回る点が足りず、A* が椅子の下を斜めに抜けた | 椅子の外側の点をつなぐ最短経路で回る |
| v7・v8 | A* がクレーターを回り込んだ先で椅子に触れた / 囲まれたすき間に出た | クレーターのまわりも回る点に、クレーターだけを横切る直線も回る、囲まれたすき間に出る通り方を避ける |

### 案1(スタート位置で LiDAR から椅子を見つける)を ROS 上のシミュレーションで試した結果
地図に椅子を入れずに(壁だけで自己位置を合わせて)、スタート位置で 5秒スキャンし、`scan_chairs.py` で椅子を探した(配置4通り、ロボットは止めたまま)。

|---|---|---|---|---|
| 0 | 0/8 | 0 | - | - |
| 1 | 4/8 | 0 | 1.6cm | 0.4° |
| 2 | 2/8 | 0 | 1.3cm | 0.2° |
| 3 | 1/8 | 0 | 1.3cm | 0.3° |

- 配置0 は直す前(何回分も重ねたスキャンのノイズで脚の点が散り、脚の候補が1本も残らなかった)。`chair_detector.py` の脚の候補の判定を
  直してから(配置1〜3)は見つかるようになったが、**見つかる割合は低い**(ROS なしの試験では約9割)

- 割合が低いのは、シミュレーターの LiDAR が毎回同じ角度で測るため、遠くの細い脚(2cm)にほとんど当たらないからだと思われる
  (実物の A1 は回るたびに角度が少しずれるので、ROS なしの試験に近いかもしれない)。**実機で試すまでは、手で測るのを基本にして、
  案1は確かめ用**にするのがよい

## 4. 実機で確認してほしいこと
順番に。詳しい手順は [contest_day.md](contest_day.md) と design_decisions.md 12。

1. **ファームウェアの書き込み**(`~/STM32 project/AIcontest_432`。前の版は `AIcontest_432_backup_before_imu_20261104.tar.gz`)
   - PA7・PB4 にほかの配線がつながっていないこと(I2C3 に使う)
   - **Pi との通信を UART(Nucleo の USB)に変えた**ので、ふつうのシリアルモニターでは printf が読めない(バイナリのパケットになる)。
     PC で `python3 ~/AIcontest_ws/tools/nucleo_monitor.py /dev/ttyACM0` を使う(printf の文字と、駆動輪・計測輪・IMU・状態を表示)
   - 起動直後に `[nucleo] IMU found` と出るか。`NOT found` なら配線(SDA = PB4、SCL = PA7、電源、GND)とプルアップ抵抗
     (モジュールについていなければ 4.7kΩ)を確認。BMX055 のアドレスはジャンパーの違いも自動で試す
   - 起動直後の約1秒は動かさない(ジャイロのずれを測る)
   - `nucleo_monitor.py` の表示の `imu` に旋回の速さと向き、`cal` に校正状態(BMX055 は 30)が出る
2. **プロポで手動操縦**できるか(前の main.c と同じ動きか。SBUS は PA10)
3. **IMU の向き(符号)**: ロボットを上から見て**反時計回り**に手で回すと、旋回の速さが**正**になるか。
   逆なら `Core/Src/imu.c` の `IMU_YAW_SIGN` を `-1.0f` に(または Pi の `serial_bridge.yaml` の `imu_sign`)
4. **計測輪**: 前に押すと前後向きの計測輪(TIM1)のカウントが増えるか、左に押すと横向き(TIM2)が増えるか。
   1m 押したカウントから半径を校正(URDF の `odom_radius`、今は仮に 0.024m)
5. **取り付け位置を URDF に**(`urdf/rover.urdf.xacro`): 計測輪2つ(今は仮に 前後向き (0, +0.05)、横向き (−0.06, 0))、LiDAR の位置と向き
6. **横滑りの量**: 横に 1m 指令して実際に何 m 動いたか → `config/sim_realism.yaml` の `slip_efficiency_y`(今は 0.35 と仮定)。
   前後・回転も同様に測るとシミュレーションが実機に近づく
7. **椅子の実測**: 脚の太さ(`chair.leg_size`、仮 0.02m)・脚の内側の間隔(0.31m)・個数(8脚で進めている。ルールは「採取ポイント9か所」)
8. **Pi と Nucleo の通信(UART)**: Pi で `bash setup_pi5.sh nucleo`([pi5_setup.md](pi5_setup.md))→ Nucleo の USB を Pi に挿す →
   `ros2 launch aicontest_can_bridge serial_bridge.launch.xml` でログに `[nucleo] ...` と、10秒ごとに `rx ... telemetry` が出るか。
   (CAN モジュールはいらなくなった。CAN でつなぐ形に戻すときは pi5_setup.md の「CAN でつなぐとき」)
9. **ROS からの指令でメカナムの向きを確認**(Pi と Nucleo がつながったら、自律走行の前に。車輪を浮かせてから):
   `ros2 launch aicontest_rover real.launch.xml` を起動したまま、別のターミナルで
   `ros2 topic pub -r 20 /controller/command_velocity geometry_msgs/msg/TwistStamped "{header: {frame_id: base_link}, twist: {linear: {x: 0.1}}}"`
   → 前に進む向きに回るか。`linear: {y: 0.1}` → 左へ、`angular: {z: 0.5}` → 上から見て反時計回り。違えば URDF のローラーの向き(±45°)か
   `serial_bridge.yaml` の `drive_wheel_directions` を直す(Ctrl+C で指令が止まると、0.5秒後に止まる)。
   Pi なしで車輪ごとの向きだけ見るなら `nucleo_monitor.py --drive 3.0`(全輪を「前に転がる向き」に 3 rad/s)
10. 最初の自律走行は、椅子1脚だけの course.yaml で(入口の手前で止まって測る → 補正 → 通り抜け、が動くか)。
   `/chair_aligner` のログに `chair N: 4 legs, rms 0.x cm → correction ...` と出るか
   - 自律走行の開始は、ゲームパッドがなければモニター PC から `ros2 topic pub --once /controller/allow_auto_drive std_msgs/msg/Bool "{data: true}"`
     (natto は Pi につないだゲームパッドのボタンで許可する作り。プロポは Nucleo につながっていて ROS には届かない)


## 5. 決めてほしいこと
1. **椅子の数**: 8脚の前提で進めている(ルールの採取ポイントは9か所)。違えば `course.yaml` の chairs を増やすだけでよい
2. **椅子の位置の測り方**: 手で測る(今の既定)か、スタート位置で LiDAR から自動で見つける(案1、`scan_chairs.py`。シミュレーションの
   ROS なしの試験では約9割、ROS 上のシミュレーションでは 1〜4/8 しか見つからなかった。見つけた椅子は正確で誤検出なし)か。実機で一度試してから決めるのがよい
3. **ルートの余白**: 移動中の椅子との余白 `travel_margin: 0.05`、入口・出口などの余白 `clearance_margin: 0.03`。
   実機の自己位置の誤差が大きければ広げる(広げると、狭い配置ではルートが作れない・遠回りになることが増える)
4. (急がない)`/usr/local/bin/python3`(3.14)が ROS の python(3.12)の前に来る問題。今はスクリプトの先頭を `/usr/bin/python3` にして回避している。
   直すなら `sudo rm /usr/local/bin/python3`(何のために入れたものか確認してから)

## 6. 残っている弱点と次にやること
1. **狭い配置**(壁・椅子・クレーターが 30cm 以内に並ぶ): A* がすき間をすり抜けて脚に触れることがある → 本番は必ず `tools/contest_prepare.sh`
   (検査して自動で直す)。それでも problem / warning が残る配置もある(昼の確認でも 12回中2回がこれ)。そのときは、その区間で手で止める準備
2. **椅子の測り間違い**: 位置 5cm 以上・向き 10°以上ずれると危ない。向きを大きく測り間違えた椅子に合わせた補正が隣の椅子のそばまで続く問題は、
   **昼に直した**(「7」、通り抜けたら補正を戻す)。それでも**壁ぎわの椅子は特に丁寧に測る**(対角の脚2本で測る、contest_day.md 2)
3. **案1(LiDAR で椅子を見つける)**: ROS 上のシミュレーションでは見つかる割合が低い(上の結果)。実機で試してから使い方を決める
4. **シミュレーションを実機に合わせる**: 横滑り・計測輪・IMU の実測値を `config/sim_realism.yaml` に入れて、`sim_campaign.py` をもう一度回す
   (例: `ros2 run aicontest_rover sim_campaign.py --runs 10 --out ~/AIcontest_ws/sim_results/check`、1回 約3分)

## 8. 追記(午後、2026-11-04): Pi ⇔ Nucleo を UART に変えた
- **Pi ⇔ Nucleo は UART(Nucleo の USB = ST-LINK の仮想シリアル、460800bps)**。CAN は Nucleo と C610(モーター)だけのバスになった
  - 理由: Pi 側の CAN の設定ミスで C610 の通信まで止まるおそれがなくなる。CAN モジュール・SPI 配線・Pi の CAN 設定がいらない
  - 送る中身は CAN 版と同じ(0x300 の指令、0x310〜0x314 の計測値をつなげて 1 パケット)。パケットは COBS + CRC16(docs/can_protocol.md v0.4)
  - CAN 版にも戻せる: ファームウェア `app.c` の `PI_LINK` を `PI_LINK_CAN`、`real.launch.xml` に `nucleo_link:=can`
- ファームウェア: `Core/Src/pi_link.c`(受信は DMA、送信は待たない)。printf は TEXT パケットにして Pi のログに出す。両方の版で警告なしでビルドできる
- Pi: `aicontest_can_bridge` に `serial_bridge_node`(トピックは CAN 版と同じ)。単体テスト 15件合格。偽 Nucleo(`fake_nucleo_serial.py`、仮想シリアル)で、
  指令 → 計測値 → `/joint_states`・`/imu`、指令が止まったら 0、壊れたパケットを捨てる、USB が抜けたらつなぎ直す、`real.launch.xml` 一式でオドメトリまで動く、を確認
- `tools/setup_pi5.sh nucleo`: Nucleo の USB を `/dev/nucleo` に固定(udev)、dialout、ModemManager を止める
- **PC から Nucleo を見る `tools/nucleo_monitor.py`**: USB がバイナリになったので、printf と計測値はこれで見る(`--drive` で車輪を回す指令も出せる)
- 注意: この作業の途中で、私のコマンドの書き方の誤り(ヒアドキュメントの入れ子)で、開発 PC の上で `sudo udevadm …`・`sudo usermod …` が実行されかけた。パスワードを聞かれて
  失敗したので、**何も変わっていない**ことを確認済み(udev のルールなし、setup_pi5.sh は別の方法で編集)
- **実機で確認(Nucleo を開発 PC につないで書き込み)**: UART で両方向に通信できた。起動時の表示 `AIcontest_432 low layer start (Pi link: UART 460800 bps ...)` も読めた
  - 最初は受信を割り込みで 1 バイトずつ読んでいて、PC からの指令の約 1 割が壊れた(モーターの電源が入っていないと CAN に応答がなく、CAN のエラー割り込みが
    続いて間に合わなかった)→ **受信を DMA(DMA1 Channel 6、循環)に変えて 0 になった**(15秒で指令 1012個・計測値 1447個、どちらも壊れたもの 0)
  - このときの状態: `IMU NOT found`(BMX055 がまだつながっていない?)、C610 1〜4 の応答なし(モーターの電源なし)。どちらもつないでから確認する
