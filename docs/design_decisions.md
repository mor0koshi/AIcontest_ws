# 設計の決定事項まとめ

最終更新: 2026-11-03

R8 宇宙AIロボット開発講座コンテストに出すローバーについて、現時点で決まっていることをまとめる。
ルールは [contest_rules.md](../contest_rules.md)、CAN通信の詳細は [can_protocol.md](can_protocol.md) を参照。

---

## 1. 全体構成

```
Raspberry Pi 5 (16GB) ── ROS 2 Jazzy + natto_library      … 上位層
   │  CAN 1Mbps(1本のバスを共有)
   ├── Nucleo-L432KC                                  … 下位層
   │     ├─ 計測輪エンコーダ ×3
   │     └─ SBUS受信機(プロポ)
   └── C610 ×4 ── M2006 ×4(メカナムホイール)
RPLIDAR A1 ── USB ── Raspberry Pi
```

### 役割分担
| 層 | 担当 | やること |
|---|---|---|
| 上位 | Raspberry Pi(ROS 2) | 自己位置推定、経路計画、経路追従、メカナムの逆運動学、オドメトリ計算、手動/自律の切り替え |
| 下位 | Nucleo-L432KC | 車輪ごとの速度PID(1kHz)、C610への電流指令、エンコーダの積算、ウォッチドッグ停止、SBUS受信 |

- Piは車輪軸の目標角速度[rad/s]を送るだけ。ギア比(36:1)の換算はNucleoが行う
- 現在のファームウェアはSTM32側でSBUSのスティック値から逆運動学まで計算しているので、逆運動学をPi側に移す

|---|---|
| 自己位置推定 | natto_mcl(LiDAR+地図)、natto_wheel_odometry |
| 経路計画・追従 | natto_astar_planner、natto_holonomic_pure_pursuit |
| 車輪指令の計算 | natto_chassis_calculator |
| 行動管理 | natto_state_machine(Mermaidの状態遷移図) |

### メカナムホイールの扱い
natto_library はメカナムに直接対応していないが、`chassis_type: "omni"` のパラメータを変えるだけで同じ計算になる(式で確認済み)。
- URDFで各車輪の向き(yaw)を**ローラー軸の向き(±45°)**にする
- 駆動輪の `wheel_radius` には**実際の半径 r ÷ √2** を入れる
- ±45°の符号は車輪の左右の種類と取り付け方(X配置/O配置)で変わるので、実機で前進・横移動・旋回を試して確認する

### オドメトリ
- **計測輪3つ**(前後向き2つ+横向き1つ、ばねで床に押し付ける)
- natto_wheel_odometry に `omni` 型として渡す(計測輪は実際の半径をそのまま入れる。ライブラリの計算には3輪以上が必要)
- 駆動輪(メカナム)は指令用で、オドメトリには使わない
- 位置推定の設定ファイルで、wheel_odometry にだけ計測輪の名前と半径を上書きする(ライブラリ本体は変更しない)
- シミュレーションでは計測輪が再現されないので、シミュレーション時は駆動輪でオドメトリを計算する

### 地図とクレーター
- コース(4m×5m)の外壁を線分、クレーターを円として地図CSVに書く
- クレーターは床なのでLiDARには映らないが、MCLは尤度場モデル(スキャン点と地図の近さで評価)なので、地図に入れても位置推定はほぼ乱れない(コードで確認済み)

## 4. CAN通信
詳細は [can_protocol.md](can_protocol.md)。

- **Pi・Nucleo・C610が1本のバスを共有**(1Mbps、標準ID)
- Pi↔Nucleoは **0x300番台**(C610の0x200番台より優先度を低くして、モーター制御を邪魔しない)
- Pi → Nucleo: 0x300 で4輪の目標角速度(100Hz)
- Nucleo → Pi: 0x310 で4輪の実速度、0x311・0x312 で計測輪のカウント累計・タイムスタンプ・状態(100Hz)
- Nucleoは0x300が100ms来なければ全モーターを停止
- Piは SocketCAN のフィルタで0x310〜0x312だけを受信(natto_canable はIDの絞り込み機能がないので使わない)
- 終端抵抗120Ωはバスの両端の2か所だけ
- バス使用率は約60〜73%の見込み

## 5. Nucleo-L432KC のピン割り当て
`~/STM32 project/AIcontest_432/AIcontest_432.ioc` の現在の設定。

| ピン | 機能 | 用途 |
|---|---|---|
| PA8 / PA9 | TIM1_CH1 / CH2(エンコーダモード) | 計測輪0 |
| PA5 / PA1 | TIM2_CH1 / CH2(エンコーダモード、32bit) | 計測輪1 |
| PB5 / PB7 | LPTIM1_IN1 / IN2(Encoder mode from IN1 IN2) | 計測輪2 |
| PA10 | USART1_RX(DMA) | SBUS受信 |
| PB6 | USART1_TX | (未使用) |
| PA11 / PA12 | CAN1_RX / TX | CANバス |
| PA2 / PA15 | USART2_TX / RX | USB仮想COMポート(デバッグ用) |
| PA0 | HSE入力 | ST-LINKからの8MHzクロック |
| PB3 | GPIO出力 | 緑LED (LD3) |
| PA13 / PA14 | SWD | 書き込み・デバッグ |
| PC14 / PC15 | LSE | 32.768kHz水晶 |

- TIM15はエンコーダモードに対応していない(CubeMXのデータで確認)ので、3つ目はLPTIM1を使う
- システムクロック 32MHz(PLL)

### SBUS設定(USART1)
100000bps、9bit(パリティ込み)、偶数パリティ、ストップビット2、**受信反転あり**(SBUSは信号が反転しているため)、DMAで受信

### CAN設定
1Mbps(32MHz、Prescaler 2、BS1 13TQ、BS2 2TQ → 16TQ/bit)

### エンコーダ設定
| タイマー | 設定 |
|---|---|
| TIM1 / TIM2 | Encoder Mode **TI1 and TI2**(両相の両エッジを数えるので分解能4倍) |
| LPTIM1 | Clock Polarity **Rising and Falling**(分解能4倍) |

- 1kHzの制御周期ごとにカウンタを読み、前回との差を符号付きで int32 の累計に足す(16bitカウンタが一周しても正しく数えられる)
- LPTIM1のカウンタは非同期なので、同じ値が2回続けて読めるまで読み直す
- Pi側で設定する「1回転あたりのカウント数」= エンコーダのPPR × 4

## 6. 開発環境のメモ
- 開発PCでは `/usr/local/bin/python3`(手動で入れた3.14)が標準の `/usr/bin/python3`(3.12)より先に見つかり、ROS 2のビルドが失敗する
  - 応急処置: ビルド時に `-DPython3_EXECUTABLE=/usr/bin/python3` を付ける
  - 恒久対策: `sudo rm /usr/local/bin/python3 /usr/local/bin/python3-config /usr/local/bin/pip3`(3.14は `python3.14` として残る)
- 開発PCはメモリ5.6GBなので、並列ビルドするとメモリが足りなくなる → `MAKEFLAGS=-j2 colcon build --parallel-workers 2`
- Pi 5(16GB)ならメモリの心配はない

```bash
cd ~/AIcontest_ws && MAKEFLAGS=-j2 colcon build --symlink-install --parallel-workers 2 \
  --cmake-args -DPython3_EXECUTABLE=/usr/bin/python3
```

### 地図の高さ(z)の決まり(natto_map / シミュレーターのコードで確認)
- 線分: z は「下端〜上端」。どちらかが0なら経路計画の地図に入る。LiDARの高さが下端〜上端の間にあればLiDARシミュレーターに映る
- 円: z=0なら経路計画の地図に入り、LiDARシミュレーターにも必ず映る
- → クレーター(床)は **z 0〜0 の線分** で描く(経路計画では避けるが、LiDARには映らない)

### シミュレーションでの確認結果
- 2回とも約35秒でゴールに到達(位置誤差 1〜2cm、向き約10°ずれ)
- クレーターとの最短距離 +6.1cm / +2.4cm(余白0.05m・最高速度0.8m/sのときは接触していた)
- 起動直後に止まる問題: `set_pose` は1回しか送られず、自己位置が出る前に届くと経路が作られない。最初の待ち時間を5秒にし、`retry_action_on_timeout:=true` で対策済み

### 椅子の下を通る(2026-11-03)
- 採取は「サンプルの上を通るだけ」でよい。椅子は脚の内側310mm(脚の太さは仮に20mm)
- 椅子の脚を地図に円(z=0)で4本入れ、`set_pose` で椅子の中心を指定すれば、nattoが脚の間を通る経路を作る
- nattoの経路計画の判定: ①ロボットの**中心**が障害物から `xy_inflation`(0.12m)以上離れる ②ロボットの**外形**(向き込み)が障害物と重ならない(余白なし)。脚の間隔はほぼ②で決まる
- 機体200×180mmなら、どちら向きでも左右55〜65mmの余裕
- シミュレーション結果(2回): 椅子の中心から2.5〜2.9cmを通過、脚との最短4.0〜4.2cm、クレーターとの最短8.6〜10.3cm、ゴール到達(向きの誤差1〜2°)
- **椅子8脚のコース(2026-11-03)**: 入口・出口は椅子の中心から0.35m、走行中の向きは0°固定(メカナムなので横にも進む)。シミュレーション2回とも、8脚すべてを中心から0.2〜1.9cmで通り抜け、脚との最短3.6〜3.7cm、クレーターとの最短18.5cm、約52秒でゴール(5秒の待ち込み)
- **椅子へは前後方向だけで突入(2026-11-03)**: メカナムは真横に滑りやすいため。入口でロボットの向きを通り抜ける向き(前進)か逆向き(後退、`allow_backward`)にそろえ、椅子の中は前後だけで進む。シミュレーション2回: 椅子の中の横の速さは最大0.04m/s(前後0.5m/s)、中心から0.2〜1.2cm、脚との最短3.3〜3.8cm(幅200mmで通るので理論上の余裕は5.5cm)、約54秒でゴール。椅子と椅子の間の移動では斜めや横の動きも残る
- 起動直後にノードの読み込みが「context is invalid」で失敗し、ロボットが動かないことが1回あった(設定と無関係の一時的なもの)。動かないときは起動し直す
- **nattoの不具合**: astar_plannerは経路の向きを「刻みの半分」ずらして出す(区間の選択は `round(deg/刻み)`、書き戻しは `(th+0.5)×刻み`)。15°刻みだと0°指定で7.5°傾いたまま走り、脚との余裕が2cm台に減っていた。刻みを2°にして回避(ずれ1°)。nattoのリポジトリに報告するとよい

## 9b. 現実に近いシミュレーション `sim_realistic.launch.xml`(2026-11-03)
```bash
ros2 launch aicontest_rover sim_realistic.launch.xml                 # 計測輪3つ
ros2 launch aicontest_rover sim_realistic.launch.xml odom_wheels:=2lr  # 計測輪2つ(前後向きを左右に)
ros2 launch aicontest_rover sim_realistic.launch.xml odom_wheels:=2fs  # 計測輪2つ(前後向き1 + 横向き1)
```

`sim.launch.xml`(理想条件)との違い:
- natto のシミュレーター部分を自分の launch で起動し直し、間に `scripts/sim_realism.py` を挟む(natto 本体は変更なし)
  - **滑り**: 指令した機体速度のうち、前後97%・横70%・旋回92%だけ効く+ゆらぎ+横流れ(`config/sim_realism.yaml`)
  - **計測輪**: 真の動きから計測輪の回転を計算し、半径の誤差(+1.5%/−1%/+2%)・ノイズ・一瞬の空転を足す。オドメトリは実機と同じく計測輪から
  - **駆動輪のエンコーダー**: 滑る前の指令どおりの回転(実機と同じ)
  - **LiDAR**: A1 に合わせて 360°・7Hz・1周360点・0.15〜12m、ノイズ1cm+取りこぼし3%
  - **置き位置の誤差**: 地図上のスタートから (+3cm, −2cm, +2°) ずらして置く
- **理想条件の `sim.launch.xml` の注意**: natto の lidar_simulation.launch.py は周期を `scan_frequency` という名前で渡すがノード側は `frequency` なので効かず、30Hz・前方180°・1周66点になっている。距離には ±1cm の一様ノイズが入る。車輪の滑りはない
- 計測輪2つのときは natto_wheel_odometry(3輪以上が必要)の代わりに `scripts/wheel_odometry_wls.py`(計測輪+重みを小さくした駆動輪の重み付き最小二乗)と `launch/localization_custom.launch.xml` を使う
- ROS を使う Python スクリプトの1行目は `#!/usr/bin/python3`(`/usr/local/bin/python3` の 3.14 では rclpy が動かない)

### スタート位置(毎回変わる)
- `course.yaml` の `start: {x, y, yaw}` だけ書けばよい。launch が `scripts/course_value.py` で読み、自己位置推定(MCL)の初期位置にする(sim / sim_realistic / real すべて)
- そのため自己位置推定は natto の localization.launch.xml ではなく `launch/localization.launch.xml`(MCL + オドメトリ。計測輪3つは natto_wheel_odometry、2つは自作)を使う
- シミュレーションのロボットは、start から `place_error_*`(既定 +3cm, −2cm, +2°)ずらして置く
- `sim.launch.xml` は `sim_realistic.launch.xml` を誤差なし(`config/sim_ideal.yaml`、置き位置の誤差0)で起動するだけになった
- 別の配置で試すときは `course_dir:=DIR`(DIR に course.yaml・line_segments.csv・circles.csv・course.md)

### 自己位置の遅れ対策(2026-11-03)
滑りも誤差もない条件でも、自己位置の誤差が 95% で 5.7cm、最大 9cm あった。原因は natto_mcl の作り:
- LiDAR のスキャンが届いたとき(A1 は約7Hz)にしか位置を出さない → 経路追従は最大 0.14秒古い位置で走っていた
- 点群を受け取ったときの粒子の位置(すでにオドメトリで進んだ後)に、少し前のスキャンを当てはめる(遅れの分だけ後ろに引っぱられる)
- natto の pointcloud2_merger(mode: merge)は最新の点群を一定周期で出し直すので、同じ古いスキャンが何度も使われ、遅れも増える

対策(natto 本体は変更なし):
- `scripts/pose_extrapolator.py`: MCL の位置(`/localization/mcl_pose` に remap)+ その後にオドメトリで進んだ分 を、オドメトリと同じ頻度(25〜54Hz)で `/localization/current_pose` に出す(`localization.launch.xml` の `extrapolate_pose`、既定 true)
- `merged_lidar_mode:=passthrough`: スキャンが届いたらすぐ1回だけ流す(sim_realistic / real の既定)
- 効果: 自己位置の誤差(95% / 最大)誤差なし 5.7 / 9.0cm → 4.1 / 6.4cm、現実に近い条件 約5〜6 / 8〜10cm → 4.6〜4.7 / 7〜9cm。r21(角度のついた椅子)で脚に −1.0cm 接触していたのが +0.8cm に

## 11d. 夜の作業で決めた・変えたこと(2026-11-04)
### 移動中も横に動かない走り方(drive_mode: forward、既定)

### 椅子の脚への接触の原因と対策(2026-11-04 深夜)
最初の本番想定のシミュレーション(10回)で4回、椅子の脚に触れた(`sim_results/2026-11-04/A0_before_axis_fix`)。1つの配置で詳しく調べた結果:
1. **入口の手前の点を、前の場所から入口へ向かう直線上に置いていた** → 横から斜めに入口へ近づき、向きはそろっても軸から横にずれたまま脚の列に入った
   → 手前の点を**通り抜けの軸の上**(入口の 15cm 手前と 30cm 手前)に置く。出口を出たあとも、軸に沿って 15cm 離れてから曲がる
2. **入口で脚を測っていた** → 補正でずれが分かっても、ロボットはその位置から出口へ一直線に向かうので、斜めに脚の列を横切った
   → **入口の 15cm 手前(中心から 0.50m)で止まって測り**、補正を受けてから入口まで進む(chair_aligner の測る範囲を 0.55m まで、補正をかける距離を 1.1m に)
3. **回りながら進むと横に数 cm ふくらむ** → 大きく回るのは入口の 30cm 手前 → 15cm 手前の区間で済ませ、15cm 手前から入口・出口まではまっすぐ
4. **経路計画が椅子の入口で輪のような経路を作った**(入口 → 横に 11cm ふくらんで戻る → 椅子の中へ)。natto の経路のなめらか化(grad_alpha)と「できるだけ入りたくない範囲」(xy_offset 0.15m)が、狭い入口で経路を脚から押し出していた
   → `xy_offset: 0.05`、`grad_alpha: 0.3`。脚との余白は経路計画用の外形を各辺 1cm 大きくしてとる(`footprint.yaml` 0.20×0.22m)、クレーターとの余白は crater_margin でとる
5. 着いたとみなす範囲 `goal_position_tolerance_m` を 3cm → 2cm
- 結果(同じ配置・同じ置き位置の誤差): 椅子7の通過位置 中心から 3.9〜4.6cm → **0.3cm**、脚との最短 −0.6〜−1.0cm → **+0.8cm**
- 補正中に MCL を止める(`hold_mcl_during_correction:=true`)は、IMU ありでも効果がはっきりしなかったので既定は false のまま

### 2回目の修正(2026-11-04 3時ごろ): 椅子の取り違え・出口からの離れ方・椅子を横切る直線

   ずれた位置・向き(最大 3.4°)で入ってしまう。1回は、正しい椅子を測った 0.6秒後に隣の椅子を測り直して上書きしていた
   → **状態機械が出した最後の目標(`/goal_pose`)が、ある椅子の通り抜けの軸の上(横のずれ 2cm 以内)にあって、ロボットがその目標に

## 11f. プログラム全体の見直し(2026-11-04 昼、実機で通る経路を中心に)
直したもの:
- **ファームウェア: printf が 1ms ごとの制御を止めていた**。`_write` が `HAL_UART_Transmit`(送り終わるまで待つ)で、115200bps の 1行(約100文字)に
  約 9ms、0.5秒ごとにモーターの速度制御が止まっていた → 文字を貯めて、`app_loop` が呼ばれるたびに送れる分だけ USART2 に入れる(割り込み不要、`app.c` の `debug_pump`)
- **ファームウェア: IMU が途中で抜けたときの再接続が約 30ms 止まる**(BMX055 の全部の初期化に待ち時間がある)→ 走っている途中はジャイロだけを
  待たずに設定し直す(`BMX055_InitGyro`)。起動時に測ったずれはそのまま使う
- **オドメトリ: ジャイロのずれの測り直し**を「計測輪が止まっている」だけで判定していたので、その場でゆっくり(約 3°/s 以下)回るときもずれとして
  引いてしまうおそれがあった → 駆動輪(モーターの実速度)も止まっているときだけにした(`wheel_odometry_wls.py`)
- 変換ノードのログ・設定の「BNO055」の表示を IMU 一般に(BMX055 を使うため)

確かめたこと(問題なし):
- トピックの受け渡し方(QoS)は実機とシミュレーションで同じ(`/joint_states`・`/imu`・`/command_joint_states`)
- 手動の速度指令が止まると、natto の twist_selector が 0.2〜0.4秒で停止を出す。Pi からの指令が止まると変換ノードが 0.5秒で 0 を送り、
  変換ノードごと落ちても Nucleo が 0.1秒で止める
- 自律走行を許可する前も状態機械は進む(待機の 5秒は過ぎる)が、許可するまでロボットは動かない(その間にジャイロのずれを測れる)

## 11g. Pi ⇔ Nucleo を UART に変更(2026-11-04 午後、ユーザーが決定)
- これまで: Pi も CAN バス(Nucleo・C610 と共有)に MCP2518FD のモジュールでつなぐ(10章)
- **今: Pi ⇔ Nucleo は UART(Nucleo の USB = ST-LINK の仮想シリアル、USART2、460800bps)、CAN は Nucleo ⇔ C610 専用**
  - 理由: Pi 側の CAN の設定ミス(水晶・ビットレート)でエラーフレームが出ると C610 の通信まで止まる。UART なら Pi に何があってもモーターのバスは無事。
    部品・配線・Pi の設定も減る。CAN を共有すると Pi は C610 のフィードバック(1秒に 4000フレーム)も全部受け取ることになっていた
  - 中身は CAN 版と同じ(0x300 の指令 / 0x310〜0x314 の計測値をつなげて 34 バイト)。パケットは COBS + CRC16(can_protocol.md v0.4)
  - ファームウェア: `pi_link.c`。受信は **DMA(DMA1 Channel 6 = USART2_RX、循環)**、割り込みは使わない(1 バイトずつの受信割り込みでは、CAN のエラー割り込みが
